## 1. Status

V3 Phase 0 is complete. This document records the implementation, local corpus profile, accepted baseline, discarded runs, and current measurement limits. The 5 EPS baseline verifies wiring and reproducibility; it is not a capacity claim.

## 3. Design Decisions

### Corpus profiling

The profiler writes accepted rows to a temporary SQLite spool in 10,000-row batches, then performs exact `GROUP BY` aggregation. Count and amount quantiles use nearest-rank positions. This keeps process memory bounded and avoids the high random-I/O cost observed with per-row indexed upserts. The cost is temporary local disk and a local/manual full-corpus run.

PaySim's one-hour source step remains the finest observed time boundary. `eventsPerUserPerSourceStep` is calculated across observed `(user, sourceStep)` groups; users absent from a step are not materialized as zero-count groups. No five-minute density is inferred from these values.

The required `transactionTypeDistribution` contains runtime-normalized types. Separate native and normalized fields are retained so source composition and runtime contract composition remain distinguishable.

### Workload ownership

`load-test/workloads/v3/workload-manifest.schema.json` defines the shared contract. The committed baseline fixes 5 EPS, 30 seconds, 150 emitted events, 50 uniformly scheduled users, seed `310519`, `HTTP_K6`, and `REBASE_TO_ARRIVAL`. The k6 scenario enforces `eventLimit` instead of assuming rate multiplied by duration is exact.

### Source metadata

Phase 0 retains source profile and time mode in test-only manifest/report artifacts. It does not add `sourceSentAt` to the event schema or Kafka headers solely for observability. Source-processing and source-transport delay are therefore intentionally absent until a source emulator owns a trustworthy timestamp.

### Time and Kafka timestamp

- k6 assigns `eventTime` from its UTC wall clock for `REBASE_TO_ARRIVAL`.
- app-api owns `receivedAt`; app-consumer owns processing start and completion clocks.
- Broker configuration was inspected as `log.message.timestamp.type=CreateTime`.
- Phase 0 exposes `fraud.kafka.producer.to.consumer.delay`, not queue latency.
- No distributed clock correction is applied. Negative durations are excluded rather than clamped.

## 5. Metric Contract

| Meter | Population |
|---|---|
| `fraud.stream.intake.receipt.persisted.total` | new receipt whose transaction commits; validation and duplicates excluded |
| `fraud.stream.kafka.publish.success.total` | committed receipt whose synchronous Kafka publish succeeded |
| `fraud.stream.kafka.publish.failure.total` | committed receipt whose publish failure status remained durable |
| `fraud.stream.consumer.delivery.total` | each invocation of the typed transaction listener, including redelivery |
| `fraud.kafka.producer.to.consumer.delay` | valid non-negative Kafka CreateTime to listener-start duration |
| `fraud.event.ingress.age` | valid non-negative `receivedAt - eventTime` on listener delivery |
| `fraud.redis.state.latency` | Redis window record/read call, including a degraded failure duration |
| `fraud.rule.processing.latency` | rule evaluation attempts after duplicate pre-check, including thrown attempts |
| `fraud.result.sink.latency` | result-sink save attempts, including duplicate-race or persistence exceptions |
| `fraud.consumer.service.latency` | every typed listener attempt from listener start through success or failure |
| `fraud.processing.log.latency` | processing-log duplicate check and persistence attempt |
| `fraud.result.precheck.latency` | fraud-result duplicate guard before Redis/Rule work |

Deserialization failures handled before the typed listener are not in the delivery/service population. Existing legacy Redis and detection Timers remain for compatibility. No meter uses event, trace, user, account, topic offset, or partition as an application tag.

After Phase 0 evidence review, the Consumer stage model was extended to expose PostgreSQL preprocessing latency before V3 Phase 1. This does not change the accepted Phase 0 baseline numbers; it adds attribution needed for the next throughput/backlog runs.

Histogram buckets are enabled and Prometheus `histogram_quantile` queries provide p50/p95/p99. Total and partition Lag come from kafka-exporter. Lag growth/drain uses a one-minute regression window sampled at the configured 15-second scrape interval; gauge decreases are drain, and counter reset semantics do not apply to the Lag gauge itself.

## 11. Known Limitations

- Source-processing and transport delay are not observable without a trustworthy source dispatch timestamp.
- `CreateTime` delay includes producer, broker, backlog, and scheduling intervals; it is not broker queue latency.
- The low-rate run does not identify sustainable EPS, a knee point, backlog growth, or recovery time.
- The normal baseline uses synthetic attributes and uniform users; it does not reproduce PaySim popularity or a controlled Kafka partition distribution.
- The full profile report and raw PaySim corpus remain local and ignored.
- Clean local startup currently requires schema-owner sequencing.

## 12. Phase 1 Readiness

Phase 1 can reuse the committed manifest contract and V3 dashboard to run longer stepped plateaus, identify sustainable EPS without predeclaring a target, and measure total/partition Lag growth and recovery. Before comparison, each run must preserve driver type, event-time mode, partition count, Consumer concurrency, and environment fingerprint.

Phase 0 completion statement:

> The same normal baseline can be reproduced, and the system can explain delay within its observed ingress age, Kafka backlog, Consumer/Redis, rule, and result-sink boundaries without claiming unavailable source or broker-queue timing.
